High-level flow

One turn, top to bottom. A plain user message runs every step; a [system] event is handled in step 0 and skips extract + validate. The three state objects on the right are read and written across steps.

INPUT — user message | [system] event
0Pre-stepcode events + lexical intents
↳ system event → skip 1 & 2 → step 3
1Extractmodel → field/value pairs
2Validatecode schema · coerce · match
3Compose · responsivecode actions the message caused
4Update statecode apply · clear pending · requeue
5Compose · agendacode the next proactive move
6Respondmodel verbalize (never decides)
OUTPUT — text + ---actions---
State (carried across turns): form_state filled fields · pending the question left open · queue unfilled required fields in schema order.

Two channels. A turn's actions merge a responsive channel (steps 0–3: what the user caused) and a proactive channel (step 5: the agenda's next move). Step 6 verbalizes the merged result, so text and actions can never disagree.

State & concepts

State objects

Validator outcomes

Step 2 turns each raw pair into exactly one outcome. The extractor emits three pair forms — {field, value} (attributed), {field, ""} (field, no value), {null, value} (value, unplaced — runs the binding cascade). Routing in step 3 is fully determined by the outcomes — no model decides it.

OutcomeWhenBecomes
VALID_SETValue present, resolves to a legal typed value.set_fields
CORRECTIONVALID_SET on a field that's already filled.set_fields overwrite + confirm in text
CHOICE_NEEDEDSelect/boolean with empty, ambiguous, or no-match value. Options come from the schema.ask_choice
CLARIFYEmpty value on a free field, or a coercion failure.text ask (a directive)
DROPPEDfield_id not in the schema (hallucinated).discarded + logged

has_new_data is derived = any VALID_SET or CORRECTION survived. It is never predicted by a model.

Binding cascade (where pending lives)

The extractor's third output form, {field_id: null, value: X}, means "I see a value but can't place it" — symmetric to the empty-value signal (field but no value). Binding an unplaced value to a field is done by code, after extraction, so pending never biases the model. Each unplaced value runs this cascade:

#RuleExample
1The model already attributed it confidently (by format / option-vocab) → done; pending not consulted.maria.g@gmail.com → email
2Else if pending exists and its type matches the value → bind to pending.pending=dob; bare date → dob (S2.2)
3Else if exactly one unfilled field of that type exists → bind there.lone date, only dob empty → dob
4Else → CLARIFY (ask which field).bare "1999" → "birth year or prior application?" (S16.2)

This is why a deflection can't force-fill pending (no unplaced value is produced — S7) and a bulk answer's confidently-typed values bind regardless of what was asked (rule 1, S16). The residual model job is honest uncertainty (emit null), not "satisfy the pending field."

Directives

A directive is a code-authored instruction handed to the responder (step 6). Directives are how deterministic decisions reach the prose without the model re-deciding them. Types:

DirectiveRaised byTells the responder to…
ackstep 0 — save/submit click or a [system] confirmationacknowledge the completed action ("Draft saved.")
fixstep 0 — [system] Validation error (carries field + server message)explain the rejection and ask for a corrected value (see S15)
missing-fieldsstep 3 — premature submit (carries the code-computed gap list)say what's still required before submitting (see S13)
ask-for-targetstep 5 — agenda targets a free-text fieldask for that field in prose (no action to render)

The responder always also receives the merged action list, so it can stitch both channels ("Saved your email — next, what's your date of birth?").

The model-risk surface

Only steps 1 and 6 are model calls; everything else is testable code. Two extractor behaviors are the residual risk — both degrade benignly:

  • Risk A — restraint stage 1: emit [] on chitchat, including turns that mention extractable-looking entities (cities, names, years). Validation can't catch a plausible-but-wrong fill; only training prevents it. (v1's R13 / doc-16 CANNOT #4.) Wrong [] → a missed fill the agenda re-asks for.
  • Risk B — honest uncertainty stage 1: attribute a value to a field only when confident; otherwise emit {null, value} and let the binding cascade place it. The old framing — "don't get seduced by pending" — is gone now that pending isn't a model input; what's left is ordinary attribution accuracy. A confident mis-attribution → visible in the form panel, fixed by a correction turn.

Eval must measure over-attribution — the rate at which the model fills a field (especially via a wrong confident attribution) when the turn didn't warrant it. That number tells us whether the null-when-unsure behavior is actually being learned. (doc-18 §6)

0  Pre-step

Before any model call, handle the two things code can settle on its own.

1  Extract

The only model call that reads input. Context = schema + form_state + recent history + the user message. No "pending" line — the last asked question is already the most-recent (least-truncated) history entry, so a dedicated pending input would be redundant, and feeding it as an expectation would bias the model toward over-attribution.

Output = a JSON list of pairs in three forms:

  • {field_id, value} — a value the model can confidently attribute by format or option-vocabulary (S1.1);
  • {field_id, ""} — a field engaged with no value → choice/clarify in step 2 (S6.1);
  • {null, value} — a value it can't place → the binding cascade in step 2 resolves it (S2.1, S16.1);
  • and the empty list [] — restraint, "no field data here" (S8.1, S9.1).

So the model's whole job is content extraction + honest uncertainty; placement of unplaced values is code. This step carries both model risks: A restraint and B honest uncertainty (see risk surface).

Appears in: S1.1S2.1S6.1S7.1S8.1S9.1S11.1S16.1

2  Validate

Turn raw pairs into typed outcomes. First, an unplaced {null, value} pair runs the binding cascade — which either attaches a field_id or routes straight to CLARIFY. Then, per attributed pair: schema membership (else DROPPED) → empty-value branch (CHOICE_NEEDED for select/bool, CLARIFY for free) → present-value branch (coerce / option-match → VALID_SET, or ambiguous/no-match → CHOICE_NEEDED). A value targeting an already-filled field becomes a CORRECTION.

multi_select (added 2026-07-21): a value naming an explicit conjunction list ("fellowship and scholarship") is split on , / & / and; if every part matches exactly one option, all are set as one list-valued VALID_SET. Anything ambiguous (a category word matching ≥2 options, e.g. "assistantship") falls through to the single-select narrowing branch → CHOICE_NEEDED subset.

Three guarantees live here: pending-binding is deterministic (not a model bias — S2.2), option lists always come from the schema (kills hallucinated options, R3 — S6.2), and a hallucinated field_id can never reach an action (S9.2).

Appears in: S1.2S2.2S3.2S5.2S6.2S9.2S10.2S16.2

4  Update state

Commit effects before the agenda runs — the proactive channel must see post-update state. Three operations: apply set_fields to form_state; if the open pending field was filled, clear it; recompute the queue.

This ordering is why "answer the last question" and "advance to the next" compose cleanly in one turn (S2.4), and why a bulk paste's many fills produce one big requeue (S11.4). When the queue empties here, step 5 goes terminal (S14.4).

Appears in: S2.4S7.4S11.4S14.4

5  Compose · agenda (proactive)

Decide the assistant's next move from post-update state. Guards skip a new agenda action when:

  • a responsive ask_choice was already emitted (≤1 per turn — the displaced target stays queued) (S5.5);
  • wants_save fired — the user is pausing, don't push (S12.5);
  • a CLARIFY outcome fired (added 2026-07-21) — the turn is already answering/clarifying a user question thread; same treatment as a responsive choice. Pending stays pending; the re-ask fires on the next quiet turn. Kills the "answer your question and circling back—" double-question pileup;
  • pending is still open/unanswered (chitchat, deflection) → re-assert in text only, never re-emit an on-screen choice (S8.5);
  • pending is confirm_submit, or the agenda is held by a fix directive (S15.5).

Otherwise next_target = head of queue: a select/boolean → ask_choice from schema options (S2.5); a free field → an ask-for-target directive (S1.5). Either way, pending = that target.

Terminal is the agenda running out of work. Empty queue → show_preview + show_button(submit), pending = confirm_submit, emitted once (S14.5). The submit flow — which had zero v1 training examples — isn't learned at all; it's a deterministic consequence of state.

Appears in: S1.5S2.5S5.5S8.5S12.5S14.5S15.5

6  Respond

The only model call that writes output. Input = context + message + the merged action list + any directives. Output = response_text, serialized by code with the actions into the canonical text + ---actions---.

Because the responder sees what actions fired, the v1 failures vanish structurally: it can't claim it did something the actions don't show (R5 text-action disconnect), and it's grounded to real state rather than free-associating (R11). It verbalizes; it never decides — every action and every directive was settled by code or step 1 already. (S1.6 stitches both channels; S13.6 a missing-fields directive; S15.6 a fix directive.)

Appears in: S1.6S13.6S15.6

Design rules (collected)

  1. Routing is derived, never predicted. has_new_data = validated extraction non-empty; choice/review/save/submit come from validator outcomes, lexical intents, and the agenda — not a model.
  2. Options always come from the schema (kills R3 hallucinated options — step 2).
  3. The agenda is code, the phrasing is model. "What to ask next" is a state cross-check (doc-16 CANNOT #3) and never reaches the model (step 5).
  4. pending is harness state, not a model input. The last asked question is already in history; binding an unplaced value to pending is done by the deterministic cascade, so it can't bias extraction (S2.2, S7).
  5. The model expresses uncertainty as data ({null, value} / {field, ""}); placement is code. Unresolvable → CLARIFY, never a silent guess (S16.2).
  6. At most one ask_choice per turn; responsive beats proactive. Displaced agenda targets stay queued (S5.5).
  7. Never re-emit an open ask_choice — re-assert in text only (S8.5).
  8. State updates before the agenda (step 4 → step 5).
  9. Terminal is the agenda running out of work — the submit flow (zero v1 training data) is not learned (S14.5).
  10. The responder verbalizes, it never decides — which removes R5 and R11 by construction (step 6).
  11. A [system] event branch may hold the agenda (validation error re-pends + holds; S15).
